# 03 — (out of phase) native backend WITHOUT the optimizer computes some `div`/`mod` results wrong

Kind: **miscompile**, native backend (arkham/nifasm), unoptimized build. The `--opt:speed` build is
the CORRECT one here, which is why the opt-vs-base oracle flagged it. Known-as: probably new
(not in bug-reports; nativenif search found only #201). Handed to the backends fuzzer's scope — not minimized.

Evidence (each confirmed against `nimony c`, which agrees with `nimony n --opt:speed`):
- `old/min/n41.nim` (reduced from seed 900041): `var i1: int = ((65535) - p5) - (p5 mod (13'u8.int or 1))`
  with p5 = -1000 → native base 67535 (as if `p5 mod 13 = -1000`), C 66547.
- `old/min/n59.nim` (seed 900059): `garr[((g0 div (arr[4] or 1'u64)) and 7'u64)] = …` in a loop writes
  garr[1] instead of garr[0] (g0 div huge = 0).
- `old/min/n223.nim` (seed 900223): `a4 = cast[int32](((v.n + v.n) mod ((v.n and gv.n) or 1'u32)))` → 0, C 5.
All three are `div`/`mod` whose divisor is `(x or 1)`; the same expression in isolation is right, so it
depends on register pressure (likely a rax/rdx clobber around `div`). Fuzzer signatures:
`n mismatch [scalarize,copyprop]`, `[imi]`, `[none]` (the "fixing" pass only perturbs registers).
Command: `nimony n -r old/min/n41.nim` vs `nimony c -r old/min/n41.nim` (compare field 12 of the t0 line).

Related, known: `[Error] \`or\`/\`sub\` with identical register operands … dropped source operand` from
nifasm on unoptimized and optimized native builds (8 native programs counted INVALID, 1 opt-only
compile failure n_optCompileFails_900123) = nim-lang/nativenif#201 (open).
