# JS/wasm backend: `{.keepOverflowFlag.}` whose operation the optimizer folded to a constant crashes jorogumo: "`c.load.kind == TagLit` into requires cursor at TagLit"

Kind: crash. Backends: JS (`nimony j`) and wasm (`nimony w`), with the optimizer on (`-d:danger`, `-d:release`, `--opt:speed`).
Known-as: new; same trigger family as bug-reports/89 (native: optimizer-folded keepovf leaves a stale flag), different
backend and symptom. Fuzzer: 100 of 232 programs failed to build on j and w with this (the most frequent finding).

Repro (`k5.nim`):
```nim
import std/syncio
proc ck(a, b: int16): int16 =
  {.keepOverflowFlag.}:
    result = a - b
proc t(i16v: int16) =
  var u = ck(i16v, i16v)
  echo u
t(5'i16)
```
Command: `nimony j -d:danger --nimcache:nc k5.nim` (also `nimony w`). Same with `int64` (`ck(v, v)` in a `case` arm).

Actual: `Error: unhandled exception: nifcore.nim(1270, 3) \`c.load.kind == TagLit\` into requires cursor at TagLit [AssertionDefect]`
from `bin/jorogumo j`. Without `-d:danger` it builds and prints `0`; C and LLVM print `0` with `-d:danger`.
Variant (1 program): the folded operand is a suffixed literal, and jorogumo reports `keepovf on unsupported op: suf`.

Expected: `0`.

Phase: shoggoth inlines `ck` and folds `i16v - i16v` to the literal `0` inside `(keepovf ...)`; jorogumo's keepovf
lowering (nativenif `src/web/codegen.nim`, the keepovf arm that `into`s the operation) assumes the operand is still
an `(add|sub|mul ...)` tag. Either the optimizer must not fold an operation under keepovf (it changes the flag's
meaning, see report 89), or jorogumo must accept a constant (flag = false).
