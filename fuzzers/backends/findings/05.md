# LLVM backend: an integer conversion of a CONSTANT is folded without truncation or zero-extension: `int64(uint32(-1'i64))` is `-1`

Kind: miscompile. Backend: LLVM (`nimony l`). Known-as: new. Fuzzer: LLVM mismatches 1000035 (`int64(uint32((-1'i64)))`)
and 1000028 (`int32(int8(a5))`-style chains on constants), 3 programs; probably also 1000177.

Repro (`l1.nim`):
```nim
import std/syncio
proc t(x: int64) =
  var a5: int64 = int64(uint32(x))
  var b: int32 = int32(int8(x))
  echo a5, " ", b
t(-1'i64)
var g = int64(uint32((-1'i64)))
echo g
```
Command: `nimony l -d:danger --nimcache:nc l1.nim` (without `-d:danger` only the global line is wrong).

Actual (LLVM, -d:danger): `-1 -1` / `-1`. Without -d:danger: `4294967295 -1` / `-1`.
Expected (C, native, JS, wasm): `4294967295 -1` / `4294967295`.

Phase: lengc LLVM, `src/lengc/llvmgenexprs.nim` conversion lowering (int→int branch, ~line 633):
"Constant integer casts fold to the target type with no instruction" does `result = val.withType(destTyp)` — it
re-labels the literal text with the new type without truncating it to the narrower width or applying the
source type's zero-/sign-extension. `uint32(-1)` must become `4294967295`, `int8(300)` must become `44`.
With the optimizer on, inlining turns the runtime case into this constant case.
