# JS backend: a `float32` literal is emitted unrounded (as the float64 value), so `3.4e38'f32` and `16777217.0'f32` keep values a float32 cannot hold

Kind: miscompile. Backend: JS (`nimony j`). Known-as: new (no bug-reports/ or nim-lang/nimony, nim-lang/nativenif match).
Fuzzer: 58 of 232 extended-run programs disagreed with C on JS; most of the float32 differences are this one
(the f32 literal reaches arithmetic, `sqrt`, `$`, comparisons, then integer results derived from them).

Repro (`jf2.nim`):
```nim
import std/[syncio, math]
proc t(p: float32) =
  var a = 3.4e38'f32
  var b = 16777217.0'f32
  var c = 1e-40'f32
  var d = p + 0.1'f32
  echo $float64(a), " ", $float64(b), " ", cast[uint32](c), " ", cast[uint32](d), " ", cast[uint32](sqrt(1e-40'f32))
t(1.0'f32)
```
Command: `nimony j --nimcache:nc jf2.nim && node nc/j/*/jf2.js` (same with `-d:danger` and without).

Actual (JS):   `3.4e+38 16777217.0 71362 1066192077 507307272`
Expected (C, LLVM, native, wasm): `3.3999999521443642e+38 16777216.0 71362 1066192077 507307239`

`cast[uint32](c)` is right because the cast rounds; a literal that flows into an f32 operation (`sqrt`, `*`) or a
widening `float64(...)` keeps its double value. wasm is right (f32.const rounds).

Phase: jorogumo JS codegen, nativenif `src/web/codegen.nim` `genSufLit` — for a float suffix it emits
`g.outp.floatLit sufFloatVal(g, t)` with no rounding to single; for `wF32` the value should be
`float64(float32(v))` (or wrapped in `Math.fround`), as `jsrender.nim` already does for f32 arithmetic results.
