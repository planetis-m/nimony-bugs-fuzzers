# 01 — ORC never collects `n.next = n` when that store is `n`'s last use (self-cycle leaks)

Kind: **miscompile (leak)** under `--mm:orc`; destructors of the cycle never run, `GC_fullCollect` does not help.
Known-as: **new** (nothing in ../bug-reports; `gh issue list -R nim-lang/nimony --search cycle / GC_fullCollect` finds nothing related).
Nim 2.4.1 `--mm:orc` collects the same program (`destroyed=1`).
Fuzzer signature: `leak:orc` (+ `diff:arc-vs-orc` through the LEAK lines). First seen at 185 s (seed 2000004), again at 354 s (seed 2001004).

## Minimized repro (`hand/leak_b.nim`)
```nim
{.feature: "lenientnils".}
import std/syncio

type
  R = object
    v: int
  Node = ref object
    r: R
    next: Node

var destroyed = 0
proc `=destroy`(x: R) = inc destroyed
proc `=wasMoved`(x: var R) = x.v = 0

proc t() =
  var n = Node(r: R(v: 15))
  n.next = n        # last use of `n`

t()
GC_fullCollect()
echo "destroyed=", destroyed

{.feature: "assumeSync".}
```

## Command
`nimony c -r --mm:orc leak_b.nim` (same with `-d:useLibc`, `--opt:speed`)

## Actual / expected
Actual `destroyed=0`. Expected `destroyed=1`.
Control experiments: add `echo n.r.v` after the store (so it is no longer the last use) -> `destroyed=1`;
a two-node cycle `n.next = m; m.next = n` -> collected (`destroyed=2`).

## Phase at fault
The duplifier treats `n` in `n.next = n` as its last read and emits a plain sink
(`destroy old n.next; n.next = n`, see the generated C: `nimDecRefCyclic(*lhs)` then
`*lhs = n` with no decRef of `n`). The reference count stays 1 (held by the object itself) and
no `nimDecRefCyclic` ever runs on the cell, so ORC never registers it as a cycle root:
with no remaining owner, the cell is unreachable and invisible to the collector.
Fix belongs either in the duplifier/mover (`isLastRead` / `genLastRead` in `src/hexer/duplifier.nim`:
a move into a location reachable through the moved value itself must be a copy + destroy under ORC,
i.e. `=dup` then let the scope-end `=destroy` decref and register the root) or in the ORC `=sink`
for cyclic ref types (register the source as a possible root). Nim 2's ORC behaves like the former.

Note: valgrind (`-d:useLibc`, `--errors-for-leak-kinds=definite`) does not report this leak — a
self-referencing block is not "definitely lost" to memcheck — so only the hook-count oracle catches it.
All 14 `leak:orc` programs of the run were re-checked with every `when defined(gcOrc): nK.next = nK`
removed (`triage_leaks.py`): all clean, so they are all this bug.
