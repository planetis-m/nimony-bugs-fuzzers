# 02 — a `lent` call in a tuple/seq constructor is `=dup`ed only after a later element has moved its source

Kind: **miscompile** (hook runs on a destroyed value: use-after-destroy / would be use-after-free for a
heap-owning type). ARC and ORC, with and without `--opt:speed`, C backend.
Known-as: **new** (../bug-reports only has #28 `let x: lent T` silently copies, unrelated; no upstream
issue for "lent dup"). Nim 2.4.1 `--mm:arc` runs the same programs correctly (no error).
Fuzzer signature: `err:dup from dead:{arc,orc,arcopt}`. First seen at 246 s (seed 2001000).

## Minimized repro (`hand/dup8.nim`; fuzzer-shaped variants `hand/dup6.nim` (tuple) and `hand/dup4.nim` (`@[...]`))
```nim
import std/syncio

type
  R = object
    id: int

var alive: array[8, bool]

proc `=destroy`(x: R) =
  if x.id != 0:
    if not alive[x.id]: echo "double destroy ", x.id
    alive[x.id] = false
proc `=wasMoved`(x: var R) = x.id = 0
proc `=dup`(s: R): R {.nodestroy.} =
  if not alive[s.id]: echo "dup from dead ", s.id
  alive[s.id + 1] = true
  result = R(id: s.id + 1)

proc borrow(x: var R): lent R = x
proc drop(x: sink R): int = 7      # destroys x

proc main =
  var x = R(id: 1)
  alive[1] = true
  let t = (borrow(x), drop(x))
  echo t[0].id, " ", t[1]

main()

{.feature: "assumeSync".}
```

## Command
`nimony c -r --mm:arc dup8.nim` (same with `--mm:orc --opt:speed`; `{.noinline.}` on the procs changes nothing)

## Actual / expected
Actual: `dup from dead 1` then `2 7` — element 0 is a `=dup` of `x` taken after `drop` already destroyed `x`.
Expected: `2 7` with no error (element 0 must be copied before `x` is moved into element 1); Nim 2.4.1
`--mm:arc` prints `2 7`. With a plain `x` instead of `borrow(x)` as element 0 the program is correct.
Scope seen so far: types with a user `=dup` hook. The same shape with `seq[int]` or an object with only a
`string` field (lifted hooks) ran clean under valgrind (`hand/uaf.nim`, `hand/uaf2.nim`), so the
hook-call path (`getHook(attachedDup)` != NoSymId in `trLocation`) is the one that defers the copy.
For a user type that owns memory this `=dup` reads freed memory.

## Phase at fault
Generated C for the fuzzer-shaped `dup6.nim` (`consume(p.b, x)` destroys `x`; both procs noinline):
```c
R* x134 = borrow(&x);                 // nimsem xelim temp: a pointer, value not materialized
R tmp135 = p.b; p.b.id = 0;
R tmp136 = x;                         // x moved: its last use
R x137 = consume(tmp135, tmp136);     // destroys x's id
R tmp138 = x137;
R xc139 = eQdup(*x134);               // the duplifier's =dup, bound by xelim_final AFTER the move
s = (tuple){ xc139, tmp138 };
```
nimsem's `xelim` (TowardsFinalIr) hoists the `lent` call into a `x.N` pointer temp; the duplifier
(`trRawConstructor` -> `trLocation` in `src/hexer/duplifier.nim`) then inserts `=dup(x.N[])` in place in
the constructor, and decides `x` in the second element is the last read (`isLastRead` / mover) — the live
borrow `x.N` of `x` is not counted as a later use. The move therefore happens before the dup. Either the
mover must treat a still-pending `lent` temp of `x` as a read of `x`, or the dup must be emitted at the
borrow temp's definition.
