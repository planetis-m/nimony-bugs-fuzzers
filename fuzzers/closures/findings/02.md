# 02: an unused local `.closure` iterator capturing a closure's parameter crashes lambdalifting

Found during generator calibration (before the timed run); also hit by the campaign as signature
`[Bug] lambdalifting treParams: captured param but no environment access`. The campaign ran with
`--avoid unused-local-iter` (every generated local iterator is used right away), so later hits come from other shapes.

## Repro (`a4.nim`)

```nim
import std/syncio

proc main() =
  let c = proc (y: int): int {.closure.} =
    result = 0
    iterator li(): int {.closure, sideEffect.} =
      yield y
  echo c(1)
main()
```

Command: `nimony c -r --nimcache:<dir> a4.nim`

## Actual

```
[Bug] lambdalifting treParams: captured param but no environment access at a4.nim(4, 8)
```

## Expected

Prints `0`. Adding `for x in li(): result = x` makes it compile and print `1`.

## Phase at fault

hexer, `lambdalifting.treParams` (src/hexer/lambdalifting.nim:1386-1434). Pass 1 records `y` as captured (by `li`),
so `localToEnv` has a field for it, but the closure literal neither owns an environment local (`ownsEnvLocal`) nor
receives one (`doAddEnvParam`): the env decision does not count captures by a nested iterator that is never turned into
a value (`emitIterValue` is the only place a capturing iterator binds its env). treParams then has nowhere to store the
parameter and reaches the `bug`.

Kind: crash. Known-as: new (nothing for "treParams" / "captured param but no environment" upstream or in ../bug-reports;
nim-lang/nimony#2378 is a different, closed nil-env bug).
