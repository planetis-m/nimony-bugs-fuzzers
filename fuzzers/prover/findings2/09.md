# 09 — A `func` writes a seq element that lies behind a `ref`/`ptr` when the write goes through `[]` (`inc n.s[0]`, `fb(h.r.s[0])`, `swap`, `var T` result)

kind: **accepts-invalid**. known-as: **new** — a remaining hole of the rule 4ba90a78 implements (fuzzers#13,
closed by 4ba90a78, was `s[0].x` with a non-`var` seq; this one is a seq that sits behind a ref/ptr).
Found by the func-rule generator: all 567 `func-accepts-invalid` log lines are this shape (path ends in a seq
element after a ref/ptr dereference: `n.s[0]`, `a[0].s[0]`, `p[].s[0]`, `n.pl.s[0]`, ...); no array-element
or plain-field write was ever accepted.

## Minimized repro (`repro/r09_func_seq_elem_behind_ref.nim`)

```nim
import std/syncio
type
  NodeObj = object
    s: seq[int]
  Node = ref NodeObj
  Holder = object
    r: Node
func fb(x: var int) = inc x
func viaInc(n: Node) = inc n.s[0]           # n.s is behind the ref
func viaVarArg(h: var Holder) = fb(h.r.s[0])  # passed to a `var` param
func viaSwap(n: Node) = swap(n.s[0], n.s[1])
func viaResult(n: var Node): var int = n.s[0] # `var T` result behind the ref
var n = Node(s: @[10, 20])
viaInc(n); echo n.s[0], " ", n.s[1]
var h = Holder(r: n)
viaVarArg(h); echo n.s[0], " ", n.s[1]
viaSwap(n); echo n.s[0], " ", n.s[1]
```

Command: `bin/nimony c -r --nimcache:nc r09_func_seq_elem_behind_ref.nim`

Actual: compiles (all four funcs), prints `11 20`, `12 20`, `20 12`: three `func`s changed the object behind `n`.
Control (`repro/r09_control.nim`): `func control(n: Node) = n.s[0] = 5` is rejected with
`cannot mutate n.s through a ref/ptr in a .noSideEffect context` (the seq goes to `[]=` as `var`).
Also accepted: the same writes in `proc {.noSideEffect.}` and `iterator`s, `+=`, and `var int` results
(`= n.s[0]`, `return`, `result = `) through `ref`, `ptr` and `ptr Obj` heads.

Expected: the error of the control for every one of them. doc/language.md, Func: "A location is 'behind a
ref/ptr' when its access path contains a dereference — `p[]`, `r.field` for a ref/ptr typed `r` ... The last
rule covers every way a location can be mutated: an assignment to it and passing it to a `var` or `out`
parameter ... a `func` cannot return a location behind a ref/ptr as its `var T` result." The access path of
`n.s[0]` contains `n.s`.

## Phase / function at fault

`src/nimony/derefs.nim: mutatesThroughPointer` walks the location from the outside in and stops at a call:
"A call that returns `var T` ends the walk: the callee answers for it." `n.s[0]` is the call
`` `[]`(n.s, 0) `` to `seqimpl.nim`'s `func [](s: seq[T]; i: int): var T`, which since 4ba90a78 writes under
`{.cast(noSideEffect).}` and takes `s` by value — so nobody answers for the dereference in its argument.
`n.s[0] = v` is caught only because it becomes `[]=` with a `var seq` parameter, where `n.s` itself is the
mutated argument. (The non-`var` seq case, `func f(s: seq[int]) = inc s[0]`, is rejected by the mutability
check: "cannot pass s[0] to var/out T parameter".)

Fix: continue the walk into the first argument of a `var`-returning accessor (or treat its argument as the
location), as the borrow checker's `rootOf`/`isAddressable` already do for `CallKinds`.

Fix risk: low-medium — funcs that bump counters in a seq held by a ref object stop compiling and need
`{.cast(noSideEffect).}` or `proc`; the stdlib built cleanly with the stricter 4ba90a78 rule, so few users.
