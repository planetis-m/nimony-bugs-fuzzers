# 06 — Incomplete (rejects-valid): true claims the prover reports as "cannot prove"

kind: **rejects-valid** (low priority, not minimized beyond these examples). known-as: partly
bug-reports/26 (offset index / `len - 1 - i`) and 29 (`in lo..hi` guard); the shapes below are not in those reports.

The run logged every rejected claim that was reached and never failed on the driver's inputs
(`findings/incomplete.log`, one line per claim: seed, kind, message). **These are candidates, not proofs**: the
driver samples ~4000 inputs per proc, so a claim such as `o.g - 1 >= 0` under `o.g >= 0` survives when no sampled
input has `o.g == 0`. The six below are universally true and were confirmed by hand
(`repro/r06_incomplete.nim`, `bin/nimony c --nimcache:nc r06_incomplete.nim`):

```nim
{.feature: "staticContracts".}
type RT = range[0..8]
proc needsRange(x, lo, hi: int): int {.requires: lo <= x and x <= hi.} = x
proc i1(a: int) =
  {.assert: min(a - 2, 7) <= 7.}              # cannot prove; `min` itself ensures result <= y
proc i2(a: int; s: seq[int]) =
  {.assert: (max(s.len, a) mod 8) < 8.}       # cannot prove
proc i3(x: int): int {.ensures: 0 <= result and result <= 7.} =   # cannot prove postcondition
  if x < 0: result = 0
  elif x > 7: result = 7
  else: result = x                            # (the `return`-per-branch spelling is proved)
proc i4(c: int): int =
  {.assume: c > 2.}
  result = needsRange(c, 3, high(int))        # cannot prove contract: lo <= x and x <= hi
proc i5(y: int): int =
  var la = default(array[2..5, int])
  result = 0
  case y
  of 4, 5: result = la[y]                     # cannot prove 'y' is in range 2..5 (`of 4..5` is proved)
  else: discard
proc i7(a: int; s: seq[int]) =
  {.assert: ((high(s) and 15) + 1) > (high(s) and 15).}   # cannot prove
```

Actual: the six `cannot prove ...` errors quoted in the comments. Expected: accepted.

Where: `src/nimony/contracts_fir.nim` (`proveCond`, `checkInRange`, the postcondition check at line ~3829).
Cause unverified; the common pattern is an operand that is not a plain location: a call carrying an `.ensures`
(`min`/`max` of an expression), `mod` inside an assertion, `result` joined over `if/elif/else`, the bound
`high(int)`, an `of a, b:` value list.

A second face of bug 02 shows up here as a wrong *violation*: `{.assert: ((-1) shr 1) <= (-1).}` is reported as
"assertion violated" although it holds at run time.
