# 06 — `return` inside a `try` (or under a `defer`) whose `finally` contains a loop: "cannot prove that result has been initialized"

kind: **rejects-valid**, in a default build (no contracts feature). known-as: **new** (not in bug-reports; upstream
"cannot prove result initialized finally"/"defer" give nothing; #1985 is a closed `case`-in-`while` variant). Not a
duplicate of prover/findings/08 (that one is accepts-invalid in handlers), possibly the same flow-join family.

## Repro (min/f06.nim)
```nim
import std/syncio

proc f(): int =
  defer:
    for i in 0..<3:
      discard
  return 1

echo f()
```
Same with `try: return 1 finally: (for i in 0..<3: discard)` (min/f06b.nim) and with a `while` loop (min/f06c.nim).
A finally WITHOUT a loop is accepted.
Command: `bin/nimony c -r --nimcache:nc min/f06.nim`
Actual: `f06.nim(3, 1) Error: cannot prove that result has been initialized`. Expected: prints `1`.
Hit 3 times by the fuzzer (b9bf9fb4def4, seeds 220012, 240017, 250018) in helpers ending in `return` with a `defer`.

## Phase / function (best reading)
`src/nimony/contracts_fir.nim` `traverseTry`: the `fin` is analysed "on the merged fall-through". When the body
ends in `return`, `c.tr.live` is false and nothing is merged, so the finally is walked on a dead path. A loop in the
finally makes the path live again (the loop's join takes the state that "landed" there — the pre-`return` state
in which `result` is not yet written), so at proc end `c.tr.live` is true with `result` uninitialised and the
init check at line ~6065 fires. The finally should be analysed once for the fall-through and its liveness must not
resurrect paths that left via `return` (or the return paths should go through the finally too).
