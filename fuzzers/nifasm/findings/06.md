# 06: `(lock <rmw> (cast (u N) (mem ..)) ..)` for N < 64 assembles a 64-bit atomic RMW

- kind: miscompile (atomics widened: touches 8 bytes, corrupts neighbours)
- known-as: new
- phase/function: `LockX64` in `genInstX64` (`src/nifasm/x64/instr.nim` ~2321 onward): the inner `AddX64/SubX64/AndX64/OrX64/XorX64/IncX64/DecX64/NegX64/NotX64` cases call the 64-bit mem emitters (e.g. `emitAdd(dest, mem, reg)`, `emitInc(dest, mem)` in `encoder.nim`, which take no width); only xadd/cmpxchg thread `intMemAccess(dest.typ).bits` through. The ordinary (non-lock) `add/sub/xadd/cmpxchg` forms DO honour the width.

Repros: `repro/lock_add_u32.nif`, `repro/lock_inc_u8.nif`:
- `(lock (add (cast (u 32) (mem (rcx))) (cast (u 32) (rax))))` -> `f0 48 01 01` = `lock add QWORD PTR [rcx],rax`; expected `f0 01 01` (`lock add dword ptr [rcx], eax`)
- `(lock (inc (cast (u 8) (mem (rcx)))))` -> `f0 48 ff 01` lock inc QWORD; expected `f0 fe 01`
Same for sub/and/or/xor/dec/neg/not at 8/16/32 bits (81 mismatch signatures in the extra pass, `lockfz.py` -> `lock.jsonl`).
Also: `(lock (add (cast (u 8) (mem ..)) (rbx)))` (64-bit reg source with an 8-bit mem) is accepted and gives the QWORD form (GNU as rejects), and `(lock (xchg|btc|bts|btr|adc|sbb ..))` are rejected ("Unsupported instruction for LOCK prefix" / sbb prefix error): known gaps, see 09.
Found by the extra pass `lockfz.py` (not part of the timed run; 516 cases).
