# 07: operand-width mismatches that GNU as rejects are accepted (the destination width wins, the source width is dropped)

- kind: accepts-invalid
- known-as: new
- phase/function: the type checks in `genInstX64` (`checkCompatibleTypes` etc.) do not compare the width of a `(cast (u N) ..)` register with the other operand. Hundreds of (mnemonic, shape) pairs, from 1610 distinct signatures in `raw.jsonl`/`log.csv` (verdict `accepts-invalid`).

Representative minimized inputs (all accepted by nifasm, all rejected by GNU as with "register type mismatch" / "operand type mismatch" / "operand size mismatch"):
- `(add (cast (u 8) (rax)) (rcx))` -> `00 c8` add al,cl (repro/add_r8_r64.nif); same for sub/and/or/xor/cmp/test/mov/adc/sbb/imul
- `(cmove (rax) (cast (u 8) (rcx)))` -> `48 0f 44 c1` cmove rax,rcx (reads all 64 bits of the 8-bit source; same for all cmovcc, bsf, bsr)
- `(and (cast (u 8) (mem (rax))) (cast (u 16) (rax)))`, `(or (cast (u 64) (mem (rax))) (cast (u 16) (rax)))`
- `(xadd (cast (u 8) (mem (rax))) (rax))`, `(cmpxchg ...)`, `(xchg ...)` with a 64-bit register against an 8/16/32-bit mem
- SSE: the memory cast is ignored, so `(movss (cast (u 16) (mem (rax))) (xmm0))`, `(addsd (xmm0) (cast (u 8) (mem (rax))))` etc. are accepted (documented for movupd/movdqu but not for the scalar ops)
- `(sete (rbp))` / setcc with a 16/32/64-bit register operand: encoded as `sete bpl` (GNU as only takes r8)
- `(mov (cast (u 8) (mem (rax))) 1000)` stores 0xe8 silently (GNU as warns "shortened")
Because these produce code that runs, a width typo in a code generator is not diagnosed.
First seen at t=0s (program 4); the family keeps growing in distinct shapes (1023 sigs at 5 min, 1610 at 45 min) but is one mechanism.
